# Kishi V2 Plugins and Two-Tier Settings

English | [中文](2026-09-08-kishi-v2-plugins.zh.md)

## Summary

Kishi can reuse DSH's persistent Host/Client plugin composition, Session controllers, model and skill registries, human interactions, and event projections. Repository assignments, backlog requests, investigation/build tickets, cross-Session attempts, and team-global settings with repository overrides remain Kishi behavior to add. The inspected extension points do not justify changing the agent loop.

This reference supports [Research DSH plugins and Kishi two-tier workflow settings](https://github.com/Kishimotovn/kishi-harness/issues/5), using DSH `c389f96bf3a9b6807cb71ed6bdad5849be0df6d8` and pinned Kishi-sb sources. The approved sequence is a decisions-only map, `/to-spec`, `/to-tickets`, then approved implementation across the phased brief. Constraints include one invited team, email/password access, DSH as the sole substrate, separate global/repository settings screens, and one GitHub issue per work item, not per Session. Firebase remains a preference, not a hosting decision. This is source/test inspection, not a deployment or runtime certification.

## Two-Tier Configuration

Kishi-sb's [actual merge](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/kishi-config.sh#L10) reads `KISHI_DEFAULTS` or the checked-in defaults, then deep-merges the repository's `.agent.yml` with `yq` multiplication: repository fields win, nested maps retain unspecified fields, and arrays replace. [Tests](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/test/tick-check.sh#L1254) cover override/inheritance. The project registry enumerates watched repositories; it is not a third behavior-settings merge layer. `KISHI_AGENT_YML` is an explicit file override.

[Model resolution](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/kishi-config.sh#L29) uses `models.plan`, `models.build`, or `models.qa` when that merged role has a provider; otherwise it uses `models.default`. [Defaults](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/config/defaults.yml#L1) select DSH `deepseek-v4-pro` by default and `deepseek-v4-flash` for build. Review uses `review.reviewers`, not `models.review`; `review.aggregator` falls back to plan, then default. [Aggregator assertions](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/test/tick-check.sh#L226) pin that chain.

Kishi's [provider dispatcher](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L451) also selects a substrate: `copilot` means hosted Copilot, `dsh` means DSH with catalog/profile/home checks, and `local` reaches Copilot BYOK. The default review panel's `local` entry therefore does not select the DSH build model. These selectors and [issue failover](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L492) are distinct from DSH LLM provider routes; V2's DSH-only decision excludes substrate failover.

DSH [settings writes](../../packages/settings/settings/src/index.ts#L668) validate and persist raw user sections before publishing resolved values. Schema defaults, composition base, and user overrides are layered; [tests](../../packages/settings/settings/tests/settings.spec.ts#L222) confirm recursive object merge and array replacement. [File persistence](../../packages/settings/settings-file/src/index.ts#L185) stores namespace sections in one YAML/JSON document. Revisions, unset, and replacement support editing, but no repository identifier or cross-namespace inheritance is implicit. Kishi still needs explicit global/repository resolution and reset semantics without copying resolved defaults into overrides.

Two traps matter. The [stock client binding](../../packages/client/ui-settings/src/client/index.ts#L58) selects memory mode on non-loopback pages; [its test](../../packages/client/ui-settings/tests/settings-scope.client.spec.ts#L438) confirms no Host reads/writes. This is not an authorization mechanism. Also, Kishi's [getter](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/kishi-config.sh#L20) discards boolean `false` through `// empty`; the [merge caller](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L1925) supplies fallback `true`. Thus YAML `auto_merge: false` does not reliably reach the HOLD policy. Preserve configurable auto-merge intent, not this defect.

<a id="section-workflow"></a>

## Workflow and Worktrees

Kishi's [spec phase](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L1246) distinguishes discussion from human go-ahead through prompting, then parses `SPEC READY`. [Ticket creation](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L1325) follows approval and creates native GitHub sub-issues/dependencies. [HITL completion](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/kishi-lib.sh#L563) also requires a human reply. V2 retains those human decisions, not keyword matching. [Merge policy](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L1919) follows QA and rechecks a QA-bypass approval against the PR head; approval invalidation therefore matters beyond initial acceptance.

The [routing helper](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/kishi-lib.sh#L495) selects grilling for `routing: grill`, otherwise Wayfinding; defaults use `routing: wayfinder` and `adopt: needs-triage`. [Review handling](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L1547) can escalate missing reviewer quorum to an operator. [Rollup](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L1973) reads `final_close_ack`, default `false`, and holds final closure for a human when enabled. AFK/HITL classification remains distinct from running state and waiting for human.

[Wrapper dispatch](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/kishi-lib.sh#L505) prefers an existing `kishi-<skill>` file, otherwise the locked base skill. [Dependency phase mapping](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/config/deps.yml#L1) references native pins rather than rewriting them. [Checkout routing](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L1430) selects the repository checkout/config; [Wayfinder execution](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/tick.sh#L1146) uses detached worktrees and preserves products on a ticket branch. [Continuity assertions](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/test/tick-check.sh#L2912) cover a clean coordinator and work surviving subsequent drives. DSH Session cwd association does not replace that ownership policy.

## Dev Note

Module placement is unapproved. Minimal candidates are a Kishi work-item/workflow owner for recorded decisions and phase resolution; a repository integration/execution owner for assignments, GitHub correlation, and worktrees; and Client plugins for backlog navigation and the two settings screens. Persistent profile composition and agent presets are the reusable assembly mechanisms, not an implementation specification.

Open decisions: storage for work items that predate/span Sessions; human identity and authorization propagation; approval revision binding, revocation, duplicate submission, and recovery after restart; re-presenting interrupted questions; whether setting changes affect active attempts; and GitHub/local-state reconciliation after partial failure. Existing plan replay does not settle these obligations.

Cross-ticket consequences: hosting research must account for a persistent execution host and native tooling, not only static Client assets. Authentication research must replace/extend launch-token trust and address the non-loopback settings binding. GitHub research needs one issue per request/ticket across attempts, native hierarchy, and idempotent completion summaries, not per-message mirroring. No Discord integration is needed. [Kishi's runtime style loader](https://github.com/Kishimotovn/kishi-sb/blob/01449124312de54e6afdea08a5116a83b78e2f1a/bin/kishi-lib.sh#L15) supplies `wait-what` for human-facing output; V2 completion summaries retain that requirement.

Evidence limit: no deployment, provider/model calls, or full tests ran. Read-only `yq` and `jq` probes confirmed nested-map/array merge behavior and boolean-false coalescing. Hosting selection, sizing, budgets, and benchmarks remain outside this research.
